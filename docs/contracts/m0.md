# Monaca M0 — binding contract

**Status:** binding for the M0 run (stage 0 + stage 1) and for the full M0 feature build that
follows it. Every agent working in this repo follows this document. Where this document and a
task description disagree, this document wins; where this document and the approved
architecture plan (`docs/architecture.md`) disagree, the plan wins and this document is a bug.

**Authority:** `docs/architecture.md` = the approved M0–M4 architecture (Chinese, verbatim).
This file = the concrete, unambiguous instantiation of its M0 slice: names, JSON shapes, DDL,
file paths and artifact names. Nothing here may be hand-waved at implementation time — if a
name is not in this file, propose it here first.

**Versioning:** this file is edited only through a PR that also updates the code it governs.

### §2.4 Native artifact placement

`.node` binaries are **CI build artifacts**, not npm packages. `@monaca/core` declares **no**
npm platform `optionalDependencies`; `packages/core/index.js` is a hand-written CommonJS loader
that looks for `<package>/monaca-core.<tuple>.node` and fails with `MONACA_CORE_BINARY_MISSING`
telling the developer to run `bun run fetch:native`. `packages/core` is `"type": "commonjs"` on
purpose, so Node and Bun both read named exports off the generated `module.exports` assignment.

`bun run fetch:native` places:

| artifact | destination | committed? |
|---|---|---|
| server binary (win) | `.monaca/bin/monaca-server.exe` | no |
| server binary (linux) | `.monaca/bin/monaca-server` | no |
| napi `.node` (win) | `packages/core/monaca-core.win32-x64-msvc.node` | no |
| napi `.node` (linux) | `packages/core/monaca-core.linux-x64-gnu.node` | no |
| generated `index.d.ts` | `packages/core/index.d.ts` | **yes** |
| generated `index.js` | not used (see below) | no |
| `openapi.json` | `spec/openapi.json` | **yes** |
| event JSON Schemas | `spec/events/*.json` | **yes** |

The generated `index.js` is intentionally **not** produced or kept: it hardcodes a "reinstall
npm dependencies" failure message that does not apply here. `packages/core/index.js` is a
committed, hand-written CommonJS loader, and the napi invocation in package.json therefore passes
`--no-js` so a build can never clobber it:

```
napi build --release --platform --no-js --dts index.d.ts
```

It must keep exporting `Verifier`, `scopeSatisfies`, `version` via static `module.exports.X = …`
assignments (that is what makes named imports work under both Node's ESM loader and Bun).

## §3 Dev modes & commands

Three modes, exactly as plan §9. All three run the **same** acceptance script.

| mode | what runs locally | Rust artifacts / PG |
|---|---|---|
| **A local full** | server + gateway + console + auth-ui | `bun run fetch:native` pulls the CI build for the current commit. PG: `DATABASE_URL` if set (needs CREATEDB/CREATEROLE), else `embedded-postgres` downloads a real PG into `.monaca/pg` — no Docker, no admin rights |
| **B remote dev** | Vue apps only, Vite proxied to the remote gateway; `--with-gateway` also runs the local gateway for module development | `deploy-dev.yml` deploys to a VPS; needs that host plus secrets |
| **C ci only** | typechecks and TS unit tests only | push, then `bun run verify:ci` (`gh workflow run` + `gh run watch`); results and Playwright reports come from artifacts |

### §3.1 Commands (the complete list)

```
bun run dev [--mode a|b|c] [--with-gateway]
    Start the local stack for the chosen mode. First run without --mode prompts and records
    the answer in .monaca/dev.json. --with-gateway is meaningful in mode b only.

bun run fetch:native [--run <id>] [--branch <b>] [--fmt] [--dry-run]
    Download CI artifacts (see §10.6) into the destinations in §2.4.
    Default: the newest rust.yml run whose head_sha == the current commit.
    --run <id>:            a specific workflow run id.
    --branch <b>:          newest run on that branch (default: current branch).
    --fmt:                 also download the "rustfmt-patch" artifact and apply it.
    --dry-run:             print the planned gh commands and destinations, download nothing.

bun run verify:ci
    Mode C. Runs `gh workflow run rust.yml|web.yml` on the current branch, waits with
    `gh run watch`, then prints per-job conclusions and downloads artifacts into
    .monaca/reports/. Non-zero exit when any required job failed.

bun run e2e:skeleton --base-url <url>
    The single acceptance script (plan §13 / this document §12). Environment-agnostic: works
    against localhost:8080, the remote dev gateway, or CI.

bun run typecheck          bun run --filter '*' typecheck && tsc -p scripts/tsconfig.json
bun test                   bun test --pass-with-no-tests (repo-wide)
bun run build              bun run --filter '*' build
```

`bun run dev` in mode A prints the exact URLs a developer should open and refuses to start a
second copy of any child process already listening on its port.

### §4.2 napi surface (`@monaca/core`)

npm package `@monaca/core` at `packages/core`; `napi.binaryName = "monaca-core"`;
targets `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`; no npm platform
`optionalDependencies`. Exact TypeScript signatures — the content of
`packages/core/index.d.ts`, regenerated by the rust.yml `codegen` job (napi-rs v3 typedef) and
committed via `bun run fetch:native`. Until the first codegen run lands, the committed file is a
hand-written placeholder with exactly these signatures:

```ts
export interface ActorChain { sub: string; act?: ActorChain }

export interface VerifiedToken {
  iss: string;
  sub: string;          // acc_… — the user, or the delegating user on an agent token
  aud: string;
  tid: string;          // ten_…
  org: string;          // org_…
  scope: string[];      // sorted, de-duplicated
  act?: ActorChain;     // present on delegated tokens only
  grantId?: string;     // grt_…, present on delegated tokens only
  jti: string;          // UUIDv7
  iat: number;          // seconds since epoch
  exp: number;
}

export interface VerifierOptions { clockSkewSecs?: number }
export interface VerifyExpectations { issuer: string; audience: string }

export declare class Verifier {
  constructor(opts?: VerifierOptions);
  setKeys(issuer: string, jwksJson: string): void;
  verifyAccessToken(token: string, expect: VerifyExpectations): VerifiedToken;
}

export declare function scopeSatisfies(granted: string[], required: string[]): boolean;
export declare function version(): string;
```

The native module performs **no I/O**: no DB, no network, no tokio runtime. Keys are pushed in
by TypeScript (`setKeys`) and cache invalidation is TypeScript's responsibility.

### §4.3 Error codes

Errors cross the napi boundary as JS `Error`s carrying a `code` property **and** a message
prefixed with the same code. `verifyAccessToken`/`setKeys` use exactly these:

| code | raised when |
|---|---|
| `MONACA_TOKEN_MALFORMED` | not a JWS, bad JSON, bad base64url, wrong segment count |
| `MONACA_TOKEN_UNKNOWN_KID` | `kid` absent from the loaded key set |
| `MONACA_TOKEN_INVALID_SIGNATURE` | signature does not verify |
| `MONACA_TOKEN_EXPIRED` | `exp` (plus skew) in the past |
| `MONACA_TOKEN_NOT_YET_VALID` | `nbf` (minus skew) in the future, or `iat` implausibly ahead |
| `MONACA_TOKEN_ISSUER_MISMATCH` | `iss` ≠ `expect.issuer` |
| `MONACA_TOKEN_AUDIENCE_MISMATCH` | neither `aud` string nor any `aud` array entry equals `expect.audience` |
| `MONACA_TOKEN_CLAIMS_INVALID` | a required claim is missing or has the wrong type |
| `MONACA_JWKS_INVALID` | JWKS is unparseable or holds no usable ES256 key |
| `MONACA_CORE_BINARY_MISSING` | (loader) no `.node` for this platform — run `bun run fetch:native` |
| `MONACA_CORE_PLATFORM_UNSUPPORTED` | (loader) platform is neither win32-x64 nor linux-x64 |

Server-side error codes use the same shape: `MONACA_` + upper snake case, documented at the
endpoint that raises them.

## §5 Data model

### §5.1 Layout

`monaca_control` (one DB) → `clusters`, `tenants`, `platform_admins`, `migration_rollup`.
`mt_<tenant_short>` (one DB per tenant):

* schema `tenant` — fixed name, **always written fully qualified** (`tenant.accounts`, …).
* schema `org_<org_short>` — one per org, **never** written qualified: resolved by
  `search_path` inside `with_org_tx`.

Identifiers are always short IDs (`[a-z0-9]{6,10}`) and always passed through `quote_ident`;
user input is never concatenated into DDL. PG role per org: `t<tenant_short>_o<org_short>`;
runtime login role `monaca_app` is a member of every org role and is created
**`WITH INHERIT FALSE`** (NOINHERIT).

Every org transaction runs:

```sql
BEGIN;
SET LOCAL search_path = org_<org_short>, tenant;   -- org first
SET LOCAL ROLE t<tshort>_o<oshort>;
-- … queries …
COMMIT;
```

`search_path` is defence in depth; the role grants are the real boundary, so a wrong
`search_path` still cannot read another org. The grants stay the real boundary **only** because
`monaca_app` is NOINHERIT: a plain `GRANT t…_o… TO monaca_app` defaults to `INHERIT TRUE`, which
hands the login role the union of every org's privileges the moment the grant runs — spike 2
(`scripts/spikes/embedded-pg.ts`) verified that a connection skipping `SET LOCAL ROLE` can then
read another org's rows, and that `WITH INHERIT FALSE` closes exactly that hole while leaving the
`SET LOCAL ROLE` path working. `MONACA_ORG_ROLE_ENFORCEMENT=1` must stay on.

### §5.2 Typed IDs

Encoded form: `<prefix>_<suffix>`. The suffix is the **TypeID v0.3 suffix encoding** of the 16
UUIDv7 bytes: treat the UUID as a 128-bit big-endian integer, prepend two zero bits (130 bits),
and emit 26 symbols of 5 bits each from the **lowercase Crockford base32** alphabet
`0123456789abcdefghjkmnpqrstvwxyz` (no `i l o u`, no padding). The first symbol is therefore
always `0`–`7`. UUIDv7 is generated in the application (`uuid` v7), never by PG.

Test vectors (both implementations must pass them):

| UUID | suffix |
|---|---|
| `00000000-0000-0000-0000-000000000000` | `00000000000000000000000000` |
| `01890a5d-ac96-774b-bcce-b302099a8057` | `01h455vb4pex5vsknk084sn02q` |
| `ffffffff-ffff-ffff-ffff-ffffffffffff` | `7zzzzzzzzzzzzzzzzzzzzzzzzz` |

`data-encoding`'s built-in base32 encodings use a different bit alignment, so the Rust side
implements this 26×5-bit loop by hand over a `u128` (≈15 lines, in `monaca-types`); TS does the
same over a `bigint`. Decoding is total: wrong length, a symbol outside the alphabet, a first
symbol above `7`, an unknown prefix, or a non-v7 version nibble is an error, never a default.

| prefix | entity | prefix | entity |
|---|---|---|---|
| `ten` | tenant | `grt` | grant |
| `org` | organization | `cli` | client (internal row id; the protocol `client_id` is a string column) |
| `acc` | account | `ses` | session |
| `agt` | agent | `evt` | audit event |
| `akey` | agent key | `dlg` | delegation |
| `apr` | approval | `int` | interaction (authorize → auth-ui handshake) |
| `key` | tenant signing key (`kid`) | `pky` | passkey (`tenant.credentials`, `kind='passkey'`) |
| `mfd` | trusted MFA device (`tenant.mfa_trusted_devices`) | `rol` | RBAC role (`tenant.roles`) |
| `res` | API resource (`tenant.api_resources`) | `inv` | organization invitation (`tenant.organization_invitations`) |
| `whk` | webhook (`tenant.webhooks`) | `dlv` | webhook delivery (`tenant.webhook_deliveries`) |

Primary keys are `uuid` columns holding UUIDv7. API responses always carry the **typed string**;
requests accept the typed string. Integer/`bigint` ids never appear in the public API.

**Exceptions — values that stay raw UUIDv7 strings (canonical hyphenated, no prefix):** the
token `jti` claim and the `jti` field of audit events. They are protocol values that standard
JWT tooling must handle untouched. A delegated token's agent identity in `act.sub` and its
`client_id` are the typed `agt_…` string.

### §5.4 Tenant provisioning saga

`CREATE DATABASE` cannot run inside a transaction, so provisioning is a resumable state machine.
Every step is idempotent, and the saga row is the tenant row itself (`state`).

| # | step | idempotency |
|---|---|---|
| 1 | insert `tenants` row, `state = 'provisioning'` | `ON CONFLICT (slug) DO NOTHING`, then re-read |
| 2 | `CREATE DATABASE mt_<short>` via `MONACA_ADMIN_DATABASE_URL` | tolerate "already exists" (SQLSTATE 42P04) |
| 3 | apply the **tenant** migration set to `mt_<short>` | each migration recorded in `tenant._migrations`; skip applied |
| 4 | create `tenant` schema objects, incl. `tenant.organizations` | part of step 3 |
| 5 | `state = 'active'` | `UPDATE … WHERE state = 'provisioning'` |

Failure leaves `state = 'provisioning'`; `monaca-server migrate` resumes from the lowest
incomplete step. Steps 2 and 3 take no lock on `tenants`, so a retry after a crash is safe.
`slug`, `short` and `db_name` are immutable after step 1.

### §5.5 Organization provisioning (one transaction)

```sql
BEGIN;
  -- 1. borrow a name that cannot collide, from the control-plane sequence space
  --    (org_short is derived from the new UUIDv7, never from user input)
  -- 2. schema
  CREATE SCHEMA org_<oshort>;
  -- 3. role
  CREATE ROLE t<tshort>_o<oshort> NOLOGIN;
  GRANT USAGE ON SCHEMA org_<oshort> TO t<tshort>_o<oshort>;
  GRANT USAGE ON SCHEMA tenant     TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA org_<oshort> TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, UPDATE, DELETE ON tenant.accounts,
        tenant.account_identifiers, tenant.credentials, tenant.sessions TO t<tshort>_o<oshort>;
  GRANT SELECT ON tenant.organizations TO t<tshort>_o<oshort>;
  GRANT SELECT, INSERT, DELETE ON tenant.agent_directory TO t<tshort>_o<oshort>;
  ALTER DEFAULT PRIVILEGES IN SCHEMA org_<oshort>
        GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO t<tshort>_o<oshort>;
  GRANT t<tshort>_o<oshort> TO monaca_app;  -- membership only: monaca_app is NOINHERIT (§5.1),
                                            -- so this confers nothing until SET LOCAL ROLE runs
  -- 4. org migration set (template)
  -- 5. register the org
  INSERT INTO tenant.organizations (id, slug, schema_name, role_name, state, created_at)
  VALUES ($1, $2, 'org_<oshort>', 't<tshort>_o<oshort>', 'active', now());
COMMIT;
```

The org's `id` uuid is generated by the application **before** the transaction; `schema_name`
and `role_name` are derived from it, so a retried transaction of the same request is a no-op
(the whole transaction rolls back and re-runs with the same derived names). `monaca_app` itself
is created by bootstrap with `WITH INHERIT FALSE` (§5.1): the grant above is deliberately
membership-only, so an org transaction that forgets `SET LOCAL ROLE` reads nothing rather than
everything.

**Authorize** (`GET /t/{tenant}/oauth2/authorize`) — required params `response_type=code`,
`client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`,
`code_challenge_method=S256`; optional `nonce`, `login_hint`, `max_age`, `resource`, `prompt`, and
the Monaca extension
`organization=<org slug>` (default: the account's membership in the tenant's `is_default` org,
else its oldest membership). An unknown `client_id` or unregistered `redirect_uri` is shown as an
error page and **never** redirected. Otherwise `response_type` other than `code`, a missing
`code_challenge`, or a method other than `S256` → redirect with `error=invalid_request`.
`login_hint` (OpenID Connect Core §3.1.2.1) is a non-binding hint for the auth-ui's identifier
field: it is trimmed, never checked against the account table and never used to authenticate, so
the endpoint cannot be used as an address oracle. `max_age` is a non-negative number of seconds:
an existing session older than that is ignored and the password is asked again.
On success the server stores an interaction (`int_…`, TTL `MONACA_INTERACTION_TTL_SECS`) and
302s to `{MONACA_AUTH_UI_URL}/sign-in?tenant={tenant}&interaction={iid}`.

**Interaction API** — the auth-ui ↔ protocol-engine handshake (Hydra-style challenge, plan §7).
The interaction id is the bearer of the request, so it is high-entropy and single-use.

```
GET /t/demo/interaction/int_01h455vb4pex5vsknk084sn02q
200 {"interaction_id":"int_…","tenant":"demo","client":{"client_id":"monaca-console","name":"Monaca Console"},
     "scopes":["openid","profile","monaca:admin"],"organization":"acme",
     "login_hint":"admin@demo.localhost","expires_at":"2026-01-01T00:10:00Z",
     "signed_in":false,"consent_required":false,"mfa_required":false}

POST /t/demo/interaction/int_…/sign-in   {"identifier":"admin@demo.localhost","password":"…"}
200 {"redirect_to":"http://localhost:5173/bff/callback?code=…&state=…"}

POST /t/demo/interaction/int_…/abort     {}
200 {"redirect_to":"http://localhost:5173/bff/callback?error=access_denied&state=…"}
```

`login_hint` repeats the authorize request's hint for the page's identifier field, or `null` when
the request had none; the page prefills it but the visitor remains free to edit it.

`sign-in` takes one `identifier` — an email address or a username — plus the `password`; an old
client may still send `email`, which is read as the identifier. A username is
`username_min_length`–`username_max_length` characters (3–32) of ASCII letters, digits, `_` or `-`,
and may not contain `@` — so the username and email namespaces cannot collide. It is stored
lowercase and resolved case-insensitively unless `username_case_sensitive=true`, which keeps the
typed case in storage and lookup (uniqueness stays case-insensitive, so two accounts can never
differ only by case). The bounds and case rule are the tenant's and apply at every
entrance: `sign-up`, `sign-up/verify`, the account centre and `PATCH /v1/accounts/{id}`. A username
already in use is `409 MONACA_USERNAME_TAKEN`; a sign-up carrying one when
`sign_up_identifiers` does not include `username` is `400 MONACA_INVALID_REQUEST`.

**Consent and authorized applications.** A third-party client (`is_third_party`) always shows the
consent screen unless the account holds an approval whose scopes cover every scope the request
asks for. `prompt=consent` shows the screen even then, while `prompt=none` with a covering approval
mints the code silently instead of answering `consent_required`. Approving records the scopes,
keyed by account and client, so approving again refreshes them in place, and answers the usual
`{"redirect_to":"…code=…"}`; denying answers the client with `error=access_denied`. Only a real
consent decision writes a grant — a first-party `prompt=consent` confirmation is not listed.

```
GET /t/demo/account/authorized-apps
200 {"items":[{"client_id":"my-app","name":"My App","scopes":["openid","profile"],
                "granted_at":"…","updated_at":"…"}],"next":null}

DELETE /t/demo/account/authorized-apps/my-app   → 204
```

`DELETE` removes the approval and revokes the account's refresh tokens for that client, so a
withdrawn application cannot renew; the next authorize request asks for consent again. A client
the account has not approved is `404 MONACA_NOT_FOUND`, and the withdrawal is audited as
`consent.revoked` on the tenant chain.

**Hosted sign-in switches.** `GET /t/{tenant}/sign-in-experience` is public and returns
`{"sign_up_enabled":…,"password_sign_in_enabled":…,"email_code_sign_in_enabled":…,"passkey_sign_in_enabled":…,"single_sign_on_enabled":…,"mfa_enabled":…,"mfa_policy":…,"mfa_trusted_devices_enabled":…,"mfa_trusted_device_ttl_days":…,"password_min_length":…,"password_min_character_types":…,"password_reject_user_info":…,"password_reject_repetition_and_sequence":…,"password_rejected_words":[…],"session_ttl_secs":…,"refresh_token_ttl_secs":…,"sign_up_identifiers":[…],"sign_up_email_verification_required":…,"username_case_sensitive":…,"username_min_length":…,"username_max_length":…,"sign_up_profile_fields":[…],"language":…,"captcha":{"enabled":…,"provider":"turnstile\|recaptcha","site_key":…,"on_sign_in":…,"on_sign_up":…,"on_password_reset":…},"branding":{"display_name":…,"logo_url":…,"dark_logo_url":…,"favicon_url":…,"primary_color":…,"terms_url":…,"privacy_url":…,"support_email":…,"website_url":…,"custom_css":…}}`
so the page can decide which forms to render, how short a password may be, how complex it must be, how long a session lasts, and how the tenant
brands the page before anyone is signed in. An optional `?client_id=` names the application whose
sign-in is starting; when that application has its own `custom_css`, it replaces
`branding.custom_css`, while every other branding field and an absent or unknown `client_id` fall
back to the tenant's values. The protocol endpoints enforce the same values: `sign-up` and `sign-up/verify` answer
`403 MONACA_SIGN_UP_DISABLED` when registration is
off, `sign-in` and `password/forgot|reset` answer `403 MONACA_PASSWORD_SIGN_IN_DISABLED` when the
password method is off, and `sign-in/code`, `sign-in/code/verify` and `sign-in/link*` answer
`403 MONACA_EMAIL_CODE_SIGN_IN_DISABLED` when emailed methods are off. At least one of the password
and email-code methods stays enabled, so the page never reaches a credential dead end. A password
that is shorter than `password_min_length` (counted in Unicode scalar values) or uses fewer than
`password_min_character_types` of ASCII lowercase letters, ASCII uppercase letters, ASCII digits
and symbols (everything else) is `400 MONACA_WEAK_PASSWORD`
at every entrance: `sign-up/verify`, `password/reset`, the account centre's password change and
`POST /v1/accounts`.
With `password_reject_user_info=true`, the password also may not contain the email's local part or
the account's username (each lowercased and only once it is at least three characters long).
With `password_reject_repetition_and_sequence=true`, it may not contain four identical characters
in a row (`aaaa`) or four ASCII alphanumeric characters in a consecutive run (`abcd`, `4321`).
Both rules answer `400 MONACA_WEAK_PASSWORD` at the same entrances.
A password containing any entry of `password_rejected_words` (compared case-insensitively) is
also `400 MONACA_WEAK_PASSWORD`. The list is stored lowercased and de-duplicated; each entry is
3–64 characters and the list holds at most 100 entries.
`session_ttl_secs` is applied when a completed sign-in writes the SSO cookie and its session row,
so the cookie's `Max-Age` and the stored `expires_at` agree; `refresh_token_ttl_secs` is applied
whenever a refresh token is issued. Both tenant values are capped by the deployment's
`MONACA_SESSION_TTL_SECS` and `MONACA_REFRESH_TOKEN_TTL_SECS`.

**Language and custom copy.** `GET /t/{tenant}/sign-in-copy?lang=…` is public and returns
`{"language":…,"default_language":…,"languages":[…],"phrases":{"signIn.title":…}}`. The hosted
page merges `phrases` over its built-in dictionary for the chosen language and announces it on
`<html lang>`; an override for a key the page does not render is dropped there, so a typo is inert
rather than copy the page cannot place. A language tag is a lowercased BCP 47-shaped tag: a 2–3
letter primary subtag, then 1–8 alphanumeric subtags, at most 35 characters. The language is
chosen in this order: an explicit `lang` when it names the tenant default or a language with
overrides; otherwise the first `Accept-Language` entry that matches one of those languages (an
exact tag first, then a configured tag matching a more specific browser tag such as `de` for
`de-AT`; `q=0` is a refusal and `*` is ignored); otherwise the tenant default. A `lang` the page
cannot show falls through to the same negotiation rather than failing the page, and `languages`
lists the default plus every language with overrides.

Management lives on `GET`/`PATCH /v1/sign-in-copy`. `GET` returns
`{"default_language":…,"languages":[{"language":…,"phrases":{…}}]}`, always listing the default
even without overrides. A `PATCH` carries `default_language`, `language` and/or `phrases`; when
`phrases` is present, `language` is required and the object is the complete replacement set for
that language — a `null` or blank value deletes one key and an empty set removes the language. The
default language always stays listed. Keys are 2–4 dotted camelCase segments
(`^[a-z][A-Za-z0-9]*(\.[a-z][A-Za-z0-9]*){1,3}$`, 3–100 characters), values are 1–500 characters
after trimming, and one language stores at most 200 overrides. Both writes land in one transaction,
and the patch is audited as `sign_in_copy.updated` with
`{"default_language","language","phrase_count"}` (`language` and `phrase_count` are `null` when
only the default changed).

**CAPTCHA and login-failure lockout.** When `captcha.enabled` is true, each flow named by
`captcha.on_sign_in`, `captcha.on_sign_up` or `captcha.on_password_reset` must carry a
`captcha_token` in its request body: `POST …/sign-in` and the code/link request steps
(`sign-in/code`, `sign-in/link`), `POST …/sign-up`, and
`POST …/password/forgot`. The server posts the tenant's secret and the token to the provider's
siteverify endpoint and proceeds only on `{"success":true}`; a missing, rejected or unverifiable
token is `400 MONACA_CAPTCHA_FAILED` and nothing else in the request is evaluated. Verify steps
that redeem a code, and the passkey endpoints, are not gated. The secret itself is never returned:
the management read reports `captcha.secret_set` only.

The lockout is keyed by the submitted identifier (lowercased) and exists only for a resolved,
active account that has a password, so an unknown address never creates a counter and the `401`
stays indistinguishable. After `login_lockout_threshold` consecutive wrong passwords (0 disables
the check; at most 100), the next attempt within `login_lockout_duration_secs` (30–86400) is
`429 MONACA_ACCOUNT_LOCKED` and is recorded on the audit chain as an
`interaction.sign_in.failed` event with reason `account_locked`. A successful sign-in deletes the
counter; an expired lock is cleared before the attempt is judged.

**Registration policy.** `sign_up_identifiers` lists the identifiers a new account may register
with; it always contains `email` and may add `username`. `sign_up_profile_fields` lists the optional
profile fields the form collects: `name` (the display name, defaulting to the address's local part)
and `avatar` (an absolute http(s) image URL of at most 2048 characters).
`sign_up_email_verification_required` decides the shape. When `true` (the default),
`POST …/sign-up` takes only `{"email":…}`, mails a code and answers
`{"verification_required":true,"expires_in":600}`; the password and profile fields belong to
`sign-up/verify`, so sending them to the request step is `400 MONACA_INVALID_REQUEST`. When
`false`, the same request creates the account and finishes the interaction, so it takes
`{"email":…,"password":…,"username":…,"display_name":…,"avatar_url":…}` and answers like
`sign-in` (a redirect, consent, or a second-factor challenge). In both shapes a profile field the
policy does not collect, a username the policy does not offer, or a password that violates the
tenant's policy is `400`.

**Email verification flows.** All four flows share one shape: a *request* call mails a 6-digit
code to the address, and a *verify* call consumes it. On success the verify call finishes the
interaction exactly like `sign-in` does (a session cookie, or `{"consent_required":true}` when the
client has not been approved yet), so the response is the same `{"redirect_to":…}` / consent body.

```
POST /t/demo/interaction/int_…/sign-up          {"email":"new@demo.localhost"}
200 {"verification_required":true,"expires_in":600}

POST /t/demo/interaction/int_…/sign-up/verify   {"email":"new@demo.localhost","code":"123456",
                                                 "password":"a-long-enough-password","display_name":"New Person",
                                                 "username":"newperson"}
200 {"redirect_to":"http://localhost:5173/bff/callback?code=…&state=…"}

POST /t/demo/interaction/int_…/sign-in/code     {"email":"new@demo.localhost"}
200 {"verification_required":true,"expires_in":600}

POST /t/demo/interaction/int_…/sign-in/code/verify {"email":"new@demo.localhost","code":"123456"}
200 {"redirect_to":"http://localhost:5173/bff/callback?code=…&state=…"}

POST /t/demo/interaction/int_…/password/forgot  {"email":"new@demo.localhost"}
200 {"verification_required":true,"expires_in":600}

POST /t/demo/interaction/int_…/password/reset   {"email":"new@demo.localhost","code":"123456",
                                                 "password":"a-different-password"}
200 {"redirect_to":"http://localhost:5173/bff/callback?code=…&state=…"}
```

Codes are six digits, valid for 600 s, single-use, and replaced by every new request for the same
address and purpose. A request within 60 s of the previous one is `429 MONACA_TOO_MANY_ATTEMPTS`;
five wrong guesses exhaust the code (`429` from then on, and only a new request can replace it),
while every other rejection is `401 MONACA_INVALID_VERIFICATION_CODE`, the same answer as an
expired, unknown or already-used code. `sign-in/code` and `password/forgot` answer the same `200`
for a known and an unknown address (a code is still minted and mailed for the unknown one, so the
timing and the response are indistinguishable), while `sign-up` answers
`409 MONACA_ACCOUNT_EXISTS`: it cannot pretend to start a registration that will never finish.
Passwords must be at least 8 characters
(`400 MONACA_WEAK_PASSWORD`). The code is stored as a SHA-256 digest only; the plaintext exists
nowhere but in the mail payload, which is written to the tenant's `outbox` under topic
`mail.verification` together with the rendered subject and body
(`{"to":…,"purpose":…,"subject":…,"body":…,"code":"…","expires_at":…}`)
and is readable in dev through `GET /internal/mail` (§6.3). A successful reset revokes every
session of that account before establishing the new one.

**Sign-in links.** `sign-in/link` answers with the same "if the address can receive mail" `200`,
but the payload is a URL carrying a 256-bit token
(`{"to":…,"purpose":"sign_in_link","subject":…,"body":…,"token":…,"url":…,"expires_at":…}`). The URL opens
`GET …/sign-in/link/verify?token=…`, which redeems the token once and signs the account in through
the same completion path as a code; a paused flow redirects to the sign-in page. The URL names no
address, so a leaked link does not disclose who it belongs to. A replay or an unknown token is
`401 MONACA_INVALID_VERIFICATION_CODE`; an address with no account fails the same generic way as
a code sign-in. The 60 s throttle applies per address and purpose.

**Security notices.** The same outbox carries code-free notices: `password_changed` to the
account's address after a password change, `email_changed` to the previous address after an email
change, and `account_deleted` to the address on file just before a self-service deletion. Each
payload is `{"to":…,"purpose":…,"subject":…,"body":…}`; §6.3's dev reader returns the newest one
per address and purpose.

**Mail copy.** Every purpose has built-in copy and an optional tenant override (§5.6
`email_templates`). Nine purposes exist: the five code mails (`sign_up`, `sign_in`,
`password_reset`, `email_change`, `delete_account`, each allowed `{{tenant}}`, `{{code}}` and
`{{expires_in}}`), `sign_in_link` (`{{tenant}}`, `{{url}}`, `{{expires_in}}`), and the three
notices (`email_changed`, `password_changed`, `account_deleted`, `{{tenant}}` only). At send time
the server substitutes the allowed placeholders into the tenant's row or, without one, into the
built-in default, and writes the result as the payload's `subject` and `body`. §6.2's
`GET /v1/email-templates` lists all nine with the effective copy, the placeholders the purpose can
render and whether a tenant row exists; `PATCH` requires both fields, trims them, enforces 1–200
characters of subject and 1–10 000 of body (counted in Unicode scalar values), and refuses a
placeholder the purpose cannot render or a `{{` that never closes with `400` — a typo would
otherwise be mailed literally to every recipient. `DELETE` drops the row and the built-in copy
applies again; it is idempotent, and a write is audited as `email_template.updated` (payload
`{"purpose","subject","body"}`) or `email_template.reset` (payload `{"purpose"}`). A tenant row
spans both fields, so a reset discards the whole override rather than one half of it.

**Delivery connector.** The outbox is the queue; `email_connector` (§5.6) is the route. While no
row exists, mail stays unpublished in `outbox` and `/internal/mail` still reads it — local and
acceptance environments need no provider. Once a tenant stores an enabled `http` route, one
in-process sender claims up to 20 unpublished `mail.verification` rows per tenant every five
seconds, posts `{"id","tenant","purpose","to","subject","text","from","from_name"}` as JSON to
the endpoint with `Authorization: Bearer <secret>` when a secret is stored, and marks the row
published only after a 2xx. A failure leaves it unpublished and counts one attempt; after five
attempts the row is abandoned, still visible to `/internal/mail`. The payload's `id` lets a
provider de-duplicate a retry whose first 2xx was lost. Templates are not involved in this step:
the posted `text` is already the rendered `body`.

The bearer secret is never echoed: `GET /v1/email-connector` answers `configured:false`, or the route plus
`secret_set`, and `PATCH` replaces the route fields while treating an omitted `secret` as
"keep", `""` as "clear" and a value as "store sealed". The endpoint must be an absolute http(s)
URL without embedded credentials; SMTP is not a provider and naming it is `400`, because a
transport would need its own TLS, bounce and retry policy rather than a column value.

**Two-step verification (TOTP).** An account may enroll one authenticator app. The four
`/t/{tenant}/account` calls authenticate with the SSO session cookie — the page that owns it is
asking about itself — and answer `401 MONACA_UNAUTHORIZED` without one.

```
POST /t/demo/account/mfa/totp            (cookie)
200 {"secret":"…base32…","otpauth_url":"otpauth://totp/Monaca:person@example.com?secret=…&issuer=Monaca&algorithm=SHA1&digits=6&period=30",
     "expires_in":600}

POST /t/demo/account/mfa/totp/verify     {"code":"123456"}
200 {"enabled":true}

DELETE /t/demo/account/mfa/totp          → 204

GET /t/demo/account
200 {"id":"acc_…","email":"person@example.com","username":null,"display_name":"Person","avatar_url":null,"has_password":true,
     "mfa":{"totp":true,"backup_codes":0,"passkeys":0,"trusted_devices":0}}

PATCH /t/demo/account                     {"display_name":"Person","username":"person","avatar_url":"https://cdn.example/person.png"}
200 {"id":"acc_…","email":"person@example.com","username":"person","display_name":"Person","avatar_url":"https://cdn.example/person.png","has_password":true,
     "mfa":{"totp":true,"backup_codes":0,"passkeys":0,"trusted_devices":0}}

GET /t/demo/account/mfa/backup-codes
200 {"remaining":10}

POST /t/demo/account/mfa/backup-codes
200 {"codes":["abcde-12345", …],"remaining":10}

DELETE /t/demo/account/mfa/backup-codes   → 204

GET /t/demo/account/mfa/devices
200 {"items":[{"id":"mfd_…","current":true,"user_agent":"…","created_at":"…",
     "last_used_at":"…","expires_at":"…"}],"next":null}

DELETE /t/demo/account/mfa/devices/{device}   → 204
```

The secret is 160 random bits, shown once as base32, and held unconfirmed for 600 s; only the
verify call writes it, sealed with the tenant's DEK, as a `tenant.credentials` row with
`kind='totp'` (§5.6), so a mistyped secret never locks an account out of its own second factor.
`POST /account/mfa/totp` on an account that already has one answers
`409 MONACA_MFA_ALREADY_ENABLED`; removal and re-enrollment is how a lost device is replaced.

**Backup codes.** An authenticator may be backed by a sheet of ten single-use recovery codes.
Each code is ten characters of the unambiguous alphabet `0123456789abcdefghjkmnpqrstvwxyz`
(no `i`, `l`, `o`, `u`), displayed as `xxxxx-xxxxx`; only the SHA-256 hash of the canonical
lowercase form reaches `tenant.backup_codes` (§5.6), never the code itself, and the plaintext is
shown exactly once in the `POST` response. Generating replaces the whole sheet atomically;
`DELETE` removes it. Both require an enrolled authenticator — backup codes recover a lost device,
they do not replace the factor itself — so `POST` without one is `400 MONACA_INVALID_REQUEST`,
and disabling TOTP removes the codes with it. `GET` reports how many remain unused.

**Trusted browsers.** A successful `POST …/mfa/verify` may carry `"remember_device": true`; when
`mfa_trusted_devices_enabled` is on, the answer also sets `monaca_mfa_device` — 32 random bytes,
hex, HttpOnly, `SameSite=Lax`, `Path=/t/{tenant}`, for `mfa_trusted_device_ttl_days` days (1–365,
default 30) — and records the row in `tenant.mfa_trusted_devices` (§5.6), which stores only the
SHA-256 of the token. Every primary proof that reaches `finish_sign_in` consults that cookie first:
a live trust for the same account completes the flow without the second factor and updates
`last_used_at`. The account centre lists the live trusts (`current` marks the browser asking) and
`DELETE` revokes one; revoking the caller's own browser also clears its cookie. A trust ends at the
configured duration, on revocation, or with the account; disabling the authenticator does not
resurrect one. While the policy is off, a `remember_device` request is ignored (no cookie is set) and
existing cookies stop skipping the challenge, so the switch retires trusts issued before it.

**Passkeys (WebAuthn).** A passkey is a discoverable credential the account registers from the
account centre and can then use as a primary factor — no email, no password — or as the second
factor. Ceremonies run at `{MONACA_AUTH_UI_URL}`, so the relying party is that origin's bare host
(`rpId`) and the origin itself is what `clientDataJSON.origin` must name; the API origin is
irrelevant to a credential. At most ten passkeys per account (`400 MONACA_INVALID_REQUEST`
beyond that). Registration options ask for `residentKey` and `userVerification` both
`required` and `attestation: "none"`; `authenticatorSelection` and `excludeCredentials` carry the
existing passkeys so the same authenticator is not enrolled twice.

```
POST /t/demo/account/passkeys/options    (cookie)
200 {"challenge":"…","rp":{"id":"localhost","name":"Monaca"},
     "user":{"id":"…","name":"person@example.com","displayName":"Person"},
     "pubKeyCredParams":[{"type":"public-key","alg":-7}],"timeout":600000,
     "attestation":"none","authenticatorSelection":{"residentKey":"required","userVerification":"required"},
     "excludeCredentials":[…]}

POST /t/demo/account/passkeys            {"rawId":"…","name":"Laptop",
                                          "response":{"clientDataJSON":"…","attestationObject":"…",
                                                      "transports":["internal"]}}
201 {"id":"pky_…","name":"Laptop","transports":["internal"],"created_at":"…","last_used_at":null}

GET  /t/demo/account/passkeys            → {"items":[{"id":"pky_…", …}]}
PATCH /t/demo/account/passkeys/{passkey} {"name":"Work laptop"} → 200 passkey object
DELETE /t/demo/account/passkeys/{passkey} → 204
```

The server verifies the `none` attestation itself: the client data names the ceremony and this
deployment's origin, the challenge is the one it issued for `reg:{account}`, the authenticator data
hashes the expected `rpId`, and the attested key is an ES256 P-256 key. Only then is a
`tenant.credentials` row with `kind='passkey'` written: `credential_id` is the raw `rawId`,
`secret_enc` the DEK-sealed COSE key, `sign_count` the reported counter, and `transports`/`name`/
`aaguid` the rest of `tenant.credentials` (§5.6). The public shape never carries the credential id.
Removing the last passkey only drops an optional factor; a password or authenticator app still
protects the account. None of these calls add an §8.1 audit action.

Passwordless sign-in is two calls on an interaction that has not signed in and is not waiting for
a second factor: `POST …/sign-in/passkey/options` returns assertion options with an **empty**
`allowCredentials` (the interaction cannot name an account, so the browser offers its discoverable
passkeys for the host), and `POST …/sign-in/passkey` takes the assertion and resolves the account
from the credential. Both are `403 MONACA_PASSKEY_SIGN_IN_DISABLED` while the tenant's
`passkey_sign_in_enabled` is off; the gate is on the shared interaction resolver, so a challenge
obtained before the switch is turned off cannot complete either. The assertion's `userHandle` must
be that account's UUID — that is what stops
one account's credential from asserting an interaction into another — and user verification must
have been performed. A rejected attempt answers `401 MONACA_INVALID_CREDENTIALS` and writes
`interaction.sign_in.failed` with a reason (`unknown_passkey`, `passkey_user_handle`,
`passkey_account_gone`, `account_disabled`, `invalid_passkey`), exactly like a wrong password.
The result after that is shared with the password path, so an enrolled second factor still pauses
the flow. The switch affects only this primary-factor path; a passkey remains an offered second
factor when the account has one.

The second factor works the same way: `POST …/mfa/passkey/options` returns assertion options scoped
to the pending account's passkeys (an account without one gets `400 MONACA_INVALID_REQUEST`), and
`POST …/mfa/passkey` verifies the assertion belongs to that account, then finishes the interaction.
Every rejection is counted by the same five-attempt budget as a wrong TOTP or recovery code, so one
factor cannot be used to reset the other.

Once enrolled, **every** primary proof — password, emailed code, sign-up, password reset — stops
at the same point: `200 {"mfa_required":true,"factors":["totp"]}`, with no session and no code
issued. When unused backup codes exist the list becomes `["totp","backup_code"]`, and `"passkey"`
is appended whenever the account has at least one passkey (it is offered without TOTP too). `GET
/interaction/{iid}` repeats `"mfa_required":true` and `mfa_factors`, so a reload resumes the step
instead of asking for the password again. `POST /interaction/{iid}/mfa/verify {"code":"123456"}`
(or `{"code":"abcde-12345","factor":"backup_code"}`) accepts the current 30-second step and one
either side (phone clocks drift) for TOTP, or one unused recovery code, then finishes the
flow exactly like a single-factor sign-in (session cookie, `{"consent_required":true}`, or
`{"redirect_to":…}`). A backup code is burned on use, and typed codes are normalised (case,
spaces and the display hyphen removed) before hashing, so the same sheet cannot be replayed. A
wrong, used or malformed code is
`401 MONACA_INVALID_VERIFICATION_CODE`; five wrong codes on one interaction answer
`429 MONACA_TOO_MANY_ATTEMPTS` (both factors share that counter, and a correct code still
completes the flow, and a fresh sign-in starts the count over). An unknown `factor` is
`400 MONACA_INVALID_REQUEST`. No audit action is
added — §8.1 stays at its fourteen — and `credentials.last_used_at` is the record that a live
factor was used.

The tenant's hosted switches decide whether this step applies at all. `mfa_enabled=false` skips it
even for an enrolled account. With `mfa_enabled=true` and `mfa_policy=mandatory`, an account with
no factor is paused on an enrollment instead: the answer is
`200 {"mfa_enrollment_required":true,"factors":["totp"]}`; `POST …/mfa/enroll` returns
`{"secret":"<base32>","otpauth_url":…,"expires_in":600}`, and
`POST …/mfa/enroll/verify {"code":"123456"}` stores the secret, marks this interaction's second
factor satisfied and finishes the flow exactly like a verified factor. The enrollment satisfies
only that interaction: every later sign-in is challenged normally. `user_controlled` keeps the
pre-policy behaviour, and an enrollment request on an interaction that is not waiting for one is
`400 MONACA_INVALID_REQUEST`.

**Account centre.** The account manages itself at the same cookie-authenticated `/t/{tenant}/account`
surface. `PATCH` accepts a `display_name` of 1–80 characters (trimmed; blank or longer is
`400 MONACA_INVALID_REQUEST`), an `avatar_url` that is either empty (clears it) or a single absolute
`http(s)` URL of at most 2048 characters, and a `username`, and answers with the same profile object
as `GET`, now including `has_password` so a passwordless account's page can hide the password form.
`avatar_url` is what the `profile` scope later exposes as the OIDC `picture` claim.

```
PATCH /t/demo/account        {"display_name":"Ada Lovelace"}
200 {"id":"acc_…","email":"person@example.com","display_name":"Ada Lovelace",
     "has_password":true,"mfa":{"totp":false,"backup_codes":0,"passkeys":0,"trusted_devices":0}}

POST /t/demo/account/password {"current_password":"…","new_password":"a-long-enough-password"}
204

GET /t/demo/account/sessions
200 {"items":[{"id":"ses_…","current":true,"client_id":"cli_…",
     "issued_at":"…","expires_at":"…","last_seen_at":"…","user_agent":"…"}],"next":null}

DELETE /t/demo/account/sessions/{session}   → 204
DELETE /t/demo/account/sessions             → 204
```

The current password is required (`401 MONACA_INVALID_CREDENTIALS` when it is wrong; an account
without a password credential answers `400`), and the new one obeys the same 8-character minimum
(`400 MONACA_WEAK_PASSWORD`). A successful change revokes every other live session, because those
browsers proved the old password; the caller's own session survives. The sessions list is the same
set the management API shows (`revoked_at IS NULL AND expires_at > now()`, newest activity first),
with `current` marking the cookie that made the request. Revoking a session that is not the caller's
own, or one that is already gone, is `404 MONACA_NOT_FOUND`; `DELETE /account/sessions` keeps the
caller and signs out the rest. Like the TOTP calls, none of these add an §8.1 audit action.

An email change is keyed by the address being claimed, not by the account, so two accounts racing
for the same address cannot redeem each other's mail; the account keeps its old address until the
code arrives. An address another account already holds is `409 MONACA_EMAIL_TAKEN` before anything
is mailed, and asking for the account's own address is `400 MONACA_INVALID_REQUEST`. Confirming
updates `accounts.primary_email` and the account's `email` identifier in one transaction, so the old
address stops signing in and the new one starts. A wrong or expired code is
`401 MONACA_INVALID_VERIFICATION_CODE`; neither call adds an §8.1 audit action.

```
200 {"verification_required":true,"expires_in":600}

POST /t/demo/account/email/verify {"email":"new@example.com","code":"123456"}
200 {"id":"acc_…","email":"new@example.com","username":null,"display_name":"Ada Lovelace",
     "has_password":true,"mfa":{"totp":false,"backup_codes":0,"passkeys":0,"trusted_devices":0}}
```

**Social sign-in** (`/t/{tenant}/connectors/*`).

A connector is configured through `/v1` (§6.2) and never exposes its secret to the public list. The
sign-in page reads `GET /t/{tenant}/connectors` and sends the browser to
`GET /t/{tenant}/connectors/{connector}/authorize?interaction={iid}`, which mints a single-use
`state` row (ten minutes) and redirects to the provider with `response_type=code`, `client_id`,
`redirect_uri={base}/t/{tenant}/connectors/{connector}/callback`, `state` and the configured
scopes. The callback redeems the state once, exchanges the code (the client secret comes out of the
sealed row), and reads an OIDC-shaped userinfo document (`sub`, `email`, `email_verified`, `name`).

An existing `(connector, sub)` link signs the account in and hands the interaction to the same
completion path a password uses, MFA and consent included. An unlinked subject is attached only
when the provider asserts `email_verified=true` and that address names an account; a verified
address with no account creates one and joins the interaction's org, so the first social sign-in is
not a dead end. An unlinked subject without a verified email is `403 MONACA_SOCIAL_UNLINKED`. The
account centre connects a provider through `GET /account/social/{connector}/authorize` (state
purpose `link`, bound to the session's account) and disconnects with
`DELETE /account/social/{connector}`; a provider account another user already holds redirects back
to the page with `?social_error=taken`. One account uses each connector at most once, and the
unique indexes are the authority on both rules. Provider failures are
`502 MONACA_SOCIAL_PROVIDER_ERROR`; a connector slug another row holds is
`409 MONACA_CONNECTOR_EXISTS`.

**Enterprise SSO** (`/t/{tenant}/sso/*`).

An SSO connector is a tenant-level OIDC identity provider configured through `/v1` (§6.2) with one
or more email domains. `GET /t/{tenant}/sso-connectors?email=…` names the connector that owns the
address's domain — an empty list when none does — so the sign-in page can route by domain without
learning the tenant's full federation map. The page sends the browser to
`GET /t/{tenant}/sso/{connector}/authorize?interaction={iid}`, which mints a single-use `state`
row (ten minutes) and redirects to the provider with `response_type=code`, `client_id`,
`redirect_uri={base}/t/{tenant}/sso/{connector}/callback`, `state` and the configured scopes
(`openid profile email` when none are named). The callback redeems the state once, exchanges the
code exactly as social sign-in does, and requires `email_verified=true`: the asserted address must
be at a domain the connector owns, otherwise it is `403 MONACA_SSO_DOMAIN_MISMATCH`; no verified
address at all is `403 MONACA_SSO_EMAIL_UNVERIFIED`. An existing account signs in; a verified
address with no account creates one and joins the interaction's org, so first-time federation is
not a dead end. Provider failures reuse `502 MONACA_SOCIAL_PROVIDER_ERROR`; a duplicate slug is
`409 MONACA_SSO_CONNECTOR_EXISTS` and a domain another connector owns is
`409 MONACA_SSO_DOMAIN_TAKEN`. While the tenant's `single_sign_on_enabled` is off, the lookup
answers `{"items":[],"next":null}` — so the page falls back to its ordinary forms — and both the
provider redirect and the callback answer `403 MONACA_SSO_DISABLED`; connectors stay configured, so
switching the method back on needs no re-registration.

**Account deletion.** `POST /account/deletion` mails a code with purpose `delete_account` to the
address on file; `POST /account/deletion/confirm {"code":…}` redeems it and deletes the account.
The store disables the account and revokes its sessions and refresh tokens first, then removes,
per org, the grants it delegated, the agents it owned (their keys, grants and delegations cascade)
and its membership, and finally deletes the tenant row — the remaining tenant tables cascade. A
failure partway leaves the account disabled and unusable rather than half-deleted. The response is
`204` and clears the session and trusted-device cookies; the audit chains keep `account.deleted`
(`{"email":…}`), because history is not account data.

The `roles` claim lists the RBAC role names assigned to the account; role permissions govern
client-registered scopes outside the standard set (`openid`, `profile`, `email`, `offline_access`,
`monaca:admin`): a sign-in requesting a scope no role grants is refused with
`403 MONACA_INSUFFICIENT_SCOPE` before the interaction is consumed.

Errors are problem+json (§6.1 end): `401 MONACA_INVALID_CREDENTIALS` (same response for an
unknown email and a wrong password), `404 MONACA_INTERACTION_NOT_FOUND`,
`410 MONACA_INTERACTION_EXPIRED`, `409 MONACA_INTERACTION_CONSUMED`, `400 MONACA_INVALID_REQUEST`.
auth-ui sends the browser to `redirect_to` with a full-page navigation.

**Token** (`POST /t/{tenant}/oauth2/token`, `application/x-www-form-urlencoded`).

* `grant_type=authorization_code` — `code`, `redirect_uri`, `client_id`, `code_verifier`.
  PKCE is mandatory; `S256` only.
* `grant_type=refresh_token` — `refresh_token`, `client_id`, optional narrower `scope`.
* `grant_type=client_credentials` — `client_id` (+ client authentication), `scope`, `resource`
  (RFC 8707), and `authorization_details` JSON array
  `[{"type":"monaca_grant","grant_id":"grt_…","resource":"…"}]` (RFC 9396).
  Every requested scope must be ⊆ the grant's scopes, else `invalid_scope`.

Client authentication: `client_secret_basic`, `client_secret_post`, or `private_key_jwt`
(§7.4). A `client_id` that names an **agent** (`agt_…`) authenticates with `private_key_jwt`
only, against the agent's registered `agent_keys`. Success response:

```json
{
  "access_token": "eyJ…",
  "token_type": "Bearer",
  "expires_in": 300,
  "scope": "tools:read"
}
```

`scope` is the space-delimited granted set. `refresh_token` appears only for
`authorization_code` when the request asked for `offline_access`; `id_token` only for
`authorization_code`. A `client_credentials` response never carries `refresh_token`.
Token errors follow **RFC 6749 §5.2** exactly —
`{"error":"invalid_request|invalid_client|invalid_grant|unauthorized_client|unsupported_grant_type|invalid_scope","error_description":"…"}`
with status 400 (401 for `invalid_client`, plus `WWW-Authenticate: Basic realm="monaca"`).
Everywhere else in the API, errors are **RFC 9457** `application/problem+json`:

```json
{ "type": "https://monaca.dev/errors/grant_revoked", "title": "Grant revoked",
  "status": 409, "detail": "grant grt_… was revoked at 2026-01-01T00:00:00Z",
  "instance": "/v1/orgs/acme/grants/01920000-…", "monaca_error_code": "MONACA_GRANT_REVOKED" }
```

**CORS.** A browser application starts a flow from its own origin, so the protocol endpoints
`/t/{tenant}/…` and the tenant's discovery document answer cross-origin reads for origins an
administrator registered on an application (§6.2 `cors_allowed_origins`). A preflight request
carries no `client_id`, so the gate is the union of every application's list within the tenant.
A registered origin receives `Access-Control-Allow-Origin: <origin>` and
`Access-Control-Allow-Credentials: true` (the hosted interaction endpoints set a session cookie);
a preflight also receives the allowed methods, the echoed requested headers and a 600-second
max-age. An unregistered origin receives no CORS headers — the browser blocks the read — and
every answer varies on `Origin`. `/v1` and `/internal/*` are not cross-origin surfaces.

### §6.2 `/v1` management API

Authentication: `Authorization: Bearer <access token>` whose `aud` is the management resource
`{base}/v1` and whose `scope` contains `monaca:admin`. Two ways to obtain one:

* **Console (BFF):** the signed-in user's own token from the `authorization_code` flow,
  requested with `resource={base}/v1`. The server grants `monaca:admin` only to accounts with
  `is_tenant_admin = true`; for anyone else the scope is silently dropped (RFC 6749 §3.3).
* **Automation / e2e:** the seeded confidential client `monaca-admin` via `client_credentials`
  with `client_secret_basic`. Its tokens use `sub = cli_…` and the tenant's default org.

Missing or invalid token → 401 + `WWW-Authenticate: Bearer`; valid but under-scoped →
**403** + `WWW-Authenticate: Bearer error="insufficient_scope", scope="monaca:admin"`.
All bodies are JSON; all ids are typed strings.

The tenant is the token's `tid`; `{org}` is an org **slug** in that tenant, so no `/t/{tenant}`
prefix appears under `/v1`. A resource outside the caller's tenant is **404**, not 403 —
existence is not disclosed.
An **agent** holding a delegated `monaca:admin` token is refused on `/v1/*`: those endpoints
require a `monaca:admin` token with **no `act` claim**.

Validation rules enforced by the server: `scopes` non-empty and each matches
`^[a-z][a-z0-9_.-]*(:[a-z][a-z0-9_.-]*)*$`; `resource` is an absolute `http(s)` URL; the grant's
`account_id` must be a member of `{org}`; the agent's `owner_account_id` must be a member of
`{org}`; `public_jwk` must be an EC P-256 public key (`kty=EC`, `crv=P-256`, no `d`) — a JWK
with a private component is **rejected** (`400 MONACA_PRIVATE_KEY_SUBMITTED`), so a careless
client can never leak a private key into the database.

An **application** (`tenant.clients`) has a protocol `client_id` chosen by the administrator: 2–32
characters of lowercase letters, digits or `-`, immutable once created. `kind=public` registers no
secret and authenticates with PKCE alone (`token_auth_method=none`); `kind=confidential` is issued a
256-bit secret, returned once on creation and once per rotation, stored only as an argon2 PHC string,
and used with `client_secret_basic`. Redirect and post-logout URIs must be absolute `http(s)` URLs;
`is_third_party` makes an authorize request show the consent screen until the account records a
covering approval, which `GET /t/{tenant}/account/authorized-apps` lists and the account can
withdraw (§6.1). A duplicate `client_id` is
`409 MONACA_CLIENT_EXISTS`; `GET`/`PATCH`/`DELETE` address the row as `cli_…`.

`custom_css` is the application's own stylesheet for the hosted page: plain CSS of at most 20,000
characters, accepted by `PATCH` only (a new application starts without one) and cleared with an
empty string. When `GET /t/{tenant}/sign-in-experience?client_id=…` names an application that has
one, that CSS replaces `branding.custom_css`; every other branding field, and the tenant CSS for
an absent or unknown `client_id`, stay the tenant's. There is no organization-level stylesheet,
so the precedence is application → tenant → built-in.

An **SSO connector** is a tenant-level OIDC provider: its slug follows the connector grammar
(2–32 lowercase letters, digits or `-`), `issuer` and the three endpoints must be absolute `http(s)`
URLs, and `email_domains` names at least one lowercase DNS domain. A domain belongs to one SSO
connector in the tenant (a duplicate is `409 MONACA_SSO_DOMAIN_TAKEN`, a duplicate slug is
`409 MONACA_SSO_CONNECTOR_EXISTS`); an empty `scopes` defaults to `openid profile email`. The
secret is sealed and never returned, and deleting the connector also drops its pending states.

**Branding** is the optional look of the hosted page, nested in the sign-in-experience object.
`display_name` replaces the tenant name (at most 64 characters); `logo_url`, `dark_logo_url`,
`favicon_url`, `terms_url`, `privacy_url` and `website_url` are absolute `http(s)` URLs; and
`primary_color` is `#rrggbb`. `dark_logo_url` is served through `prefers-color-scheme: dark`, so a
tenant may carry a light and a dark mark; a tenant with only `dark_logo_url` sees it in both
schemes. `favicon_url` replaces the document icon, and `support_email` (a single address of at
most 254 characters) and `website_url` join the legal links under the card. `custom_css` is plain
CSS appended after the built-in stylesheet (at most 20 000 characters; no HTML or JavaScript — the
page writes it into a `<style>` element's text, so it cannot escape the tag). An absent field keeps
its value and an empty string clears it, so a tenant can remove a logo without a second endpoint.
The page falls back to its built-in mark, name and palette whenever a field is null. Branding
applies to the hosted sign-in page; the console's own chrome stays neutral.

A **webhook** subscribes an absolute `http(s)` endpoint to audit actions. `events` is a non-empty
subset of the catalog below, de-duplicated and case-sensitive; `enabled=false` pauses deliveries
without deleting the history. The signing key (`whsec_` + 64 hex characters, 256 bits) is generated
on creation, sealed at rest, returned once and replaced by `POST …/secret`. Each delivery is a
`POST` with `content-type: application/json`, `x-monaca-event: <action>`, and
`x-monaca-signature: sha256=<lowercase hex HMAC-SHA256 over the exact request body, keyed with the
signing key>`. The body is
`{"hook_id":"whk_…","event":"account.created","created_at":…,"data":<the §8.1 audit event>}`.
A 2xx answer is success; anything else is retried twice (after 0.5 s and 1.5 s) and then recorded in
`webhook_deliveries` with the last status, the attempt count and the last error. Delivery happens
after the audit row commits and never blocks the request that produced it. The catalog is the set
of actions appended through the tenant and org audit helpers — account, client, connector,
organization, resource, role, session, sign-in, sign-in-experience and webhook actions; actions
written directly into an org schema inside a business transaction (member, agent and grant changes)
are not subscribable yet.

An **API resource** registers an absolute `http(s)` identifier and the scope names it defines. When
an authorize request names a registered indicator as `resource`, every non-standard scope it asks
for must be one of that resource's scopes; otherwise the request redirects with
`error=invalid_scope` before the page opens. An indicator that is not registered keeps the
pre-registry behaviour, because agent/MCP flows use resource URLs outside tenant configuration. A
duplicate identifier is `409 MONACA_RESOURCE_EXISTS`; the row id is `res_…`.

An **organization** is created through the provisioning transaction of §5.5: its slug matches
`^[a-z0-9][a-z0-9-]{1,30}$`, is unique in the tenant, and a duplicate is
`409 MONACA_ORG_EXISTS`; the row id is `org_…`. `GET /v1/orgs` and `GET /v1/orgs/{org}` report
both states, and `{org}` is a slug or an `org_…` id, so an archived org stays addressable.
`PATCH {"state":"archived"}` is the reversible substitute for a hard delete — the schema and its
audit chain stay, but the slug stops resolving in `authorize` and in the `/v1/orgs/{org}/…`
sub-resources; `{"state":"active"}` restores both. Repeating the current state is a no-op and
writes no second audit event, and the default organization (`is_default`, the fallback for every
flow that names no org) cannot be archived: that `PATCH` is `400`.

An organization may also register its **email domains**: domains are case-insensitive (stored
lowercased), belong to at most one org in the tenant (a duplicate is `409 MONACA_DOMAIN_EXISTS`),
and gate just-in-time membership. A sign-in (password, emailed code, sign-up or social) that names
an org and lands on an account that is not yet a member joins it with role `member` when the
account's primary email domain is registered to that org; the join writes `org.member.added` with
`"jit": true`. A sign-in from any other domain keeps the ordinary `403 MONACA_INSUFFICIENT_SCOPE`.
Removing a domain stops future joins but leaves the memberships it already created.

An **organization invitation** names one address and the role (`owner`/`admin`/`member`, default
`member`) it receives on joining; `expires_in_days` is 1–90 (default 7), and the invitation carries
no token — acceptance is the invited account signing in, matched case-insensitively against its
primary email. At sign-in the invitation is checked before the email-domain rule, so an invited
`admin` joins as `admin` rather than being downgraded to `member`; the join writes
`org.member.added` with the invitation id and `"jit": false`, and the row is marked accepted.
Accepted and expired invitations are not listed, and re-inviting an expired address replaces the
stale row instead of conflicting. Revoking a live invitation is immediate: the next sign-in falls
back to the ordinary membership and domain rules.

An **organization role** is a named scope set defined inside one org: its name is unique within
the org (a duplicate is `409 MONACA_ORG_ROLE_EXISTS`), its scopes follow the ordinary scope grammar,
and its row id is `rol_…`. A member may hold any number of them; the scopes they grant count only
while signing into that org, so a sign-in asking for one of them passes §6.2 scope enforcement and
the resulting id_token lists them in `org_roles` (§7.3). The membership rank in `members.role`
(owner/admin/member) is separate and confers no scope.

### §6.3 `/internal/*`

Authenticated by `X-Monaca-Internal-Secret: $MONACA_INTERNAL_SECRET` (constant-time compare);
wrong or missing → 401 with no detail. M1 replaces this with mTLS.

| method | path | request | response |
|---|---|---|---|
| POST | `/internal/audit` | `{"tenant":"demo","org":"acme","event":{…§8.1…}}` | 201 `{"seq":42,"hash":"<64 hex>"}` |
| GET | `/internal/audit?tenant=demo&action=…&limit=…&before=…` | query: `tenant` (required), `action`/`before` (optional), `limit` (optional, 1–200) | 200 `{"items":[…§8.1 events…],"next":…,"head":{"seq":…,"hash":"…"}}` — the tenant chain, newest first |
| GET | `/internal/tenants/{slug}/jwks` | — | 200 JWKS document (used by the gateway's first sync) |
| GET | `/internal/tenants/{slug}/issuer` | — | 200 `{"issuer":"…","audiences":["…"]}` |
| GET | `/internal/health` | — | 200 `{"status":"ok","db":"ok"}` |
| GET | `/internal/mail?tenant=demo&to=…&purpose=…` | query: `tenant` (required), `to` (required), `purpose` (optional: one of the nine mail purposes) | 200 `{"to":"…","topic":"mail.verification","payload":{"to":"…","purpose":"…","subject":"…","body":"…","code":"…","expires_at":…}}`; the payload matches the purpose (a link mail carries `token`/`url`, a notice carries no code); 404 when no mail matches |

`GET /internal/mail` returns the newest `mail.verification` outbox entry for an address, which is
how dev and `e2e:skeleton` read the code that was "emailed" (§6.1). It is a dev affordance, not a
delivery mechanism: production replaces the outbox consumer with a real sender and this endpoint
goes away.

This is the only interface through which the Bun side writes core data (plan §1): modules write
audit events here, never directly into `audit_events`.

## §7 Token formats

All tokens are JWS compact, `alg = ES256`, signed with the tenant's active `signing_keys` row;
`kid` is that row's `id`. Every token header carries `"typ"`.

### §7.1 User access token

Header `{"alg":"ES256","kid":"<uuid>","typ":"at+jwt"}`; claims:

```json
{
  "iss": "http://localhost:8080/t/demo",
  "sub": "acc_00000000000000000000000000",
  "aud": "http://localhost:8080/mcp/demo",
  "tid": "ten_00000000000000000000000000",
  "org": "org_00000000000000000000000000",
  "scope": ["tools:read"],
  "jti": "01920000-0000-7000-8000-000000000000",
  "iat": 1767225600,
  "exp": 1767226500
}
```

### §7.2 Agent-delegated token

Same, plus `act` and `grant_id`, with `sub` remaining the **delegator account**:

```json
{
  "iss": "http://localhost:8080/t/demo",
  "sub": "acc_00000000000000000000000000",
  "aud": "http://localhost:8080/mcp/demo",
  "tid": "ten_00000000000000000000000000",
  "org": "org_00000000000000000000000000",
  "scope": ["tools:read"],
  "act": { "sub": "agt_00000000000000000000000000" },
  "grant_id": "grt_00000000000000000000000000",
  "jti": "01920000-0000-7000-8000-000000000001",
  "iat": 1767225600,
  "exp": 1767225900
}
```

TTL is fixed at **300 s** and is not configurable. `scope` is the intersection of the grant's
scopes and the requested scopes: **never a union**, `aud` only narrows, `exp` only shortens
(plan §5). Multi-hop nesting (`act.act`) is M3; the verifier must already handle arbitrary depth.

### §7.3 id_token

Header `{"alg":"ES256","kid":"…","typ":"JWT"}`; claims `iss`, `sub` (account id), `aud`
(client_id), `tid`, `org`, `iat`, `exp`, `nonce` (echoed when the authorize request supplied
one). M0 issues `email` and `name` only for `scope` containing `email`/`profile`. M1 also issues
`picture` (the account's `avatar_url`) for `profile`, `auth_time`, `at_hash`, and `roles` — the
names of the RBAC roles assigned to the account, omitted
when it holds none (§6.2). It also carries `org_roles` — the organization roles the account holds
in the token's `org`, omitted when it holds none. `org_roles` scopes are what let an org role grant
a scope for that org only, while `roles` (tenant roles) grant it everywhere. The UserInfo endpoint
exposes the same `profile`-scoped `name` and `picture`, always carries `sub`, and adds `email` and
`email_verified` under the `email` scope.

### §7.4 Client assertion (`private_key_jwt`)

`client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`,
`client_assertion=<JWT>`. Required claims: `iss` **and** `sub` both equal the `client_id`;
`aud` equal to the **token endpoint URL exactly** (`http://localhost:8080/t/demo/oauth2/token`);
`exp` ≤ `iat` + 300 s; `jti` present and **single-use** (replay → `invalid_client`). Signature
verified against the client's registered JWKS (for a client) or the agent's registered
`agent_keys` (for an agent acting as a client). An assertion that is valid but not permitted for
the requested grant → `invalid_grant`; a bad signature → `invalid_client`.

## §8 Audit

### §8.1 Event JSON

```json
{
  "id": "evt_00000000000000000000000000",
  "at": "2026-01-01T00:00:00.000Z",
  "action": "agent.token.issued",
  "actor_chain": [
    { "type": "account", "id": "acc_00000000000000000000000000" },
    { "type": "agent",   "id": "agt_00000000000000000000000000" }
  ],
  "subject": { "type": "grant", "id": "grt_00000000000000000000000000" },
  "decision": "allow",
  "grant_id": "grt_00000000000000000000000000",
  "jti": "01920000-0000-7000-8000-000000000001",
  "payload": { "scope": ["tools:read"], "aud": "http://localhost:8080/mcp/demo" }
}
```

Rules: `actor_chain` is ordered outermost-first and is **never empty**; `decision` is
`allow` | `deny` | `info`; `payload` is an object (never an array, never `null`); `at` is
millisecond precision UTC. The stored form adds `seq`, `prev_hash` and `hash` (§5.7); those three
are **excluded** from the canonical bytes (§8.2) — everything else in this object is included
verbatim, so the JSON Schema in `spec/events/` is exactly this object minus those three keys.

`subject_type`/`subject.id` come from the `subject` object: `subject.type` ∈
`account` | `org` | `agent` | `agent_key` | `grant` | `client` | `tool` | `session` | `tenant`;
`subject.id` is the typed id string (a tool name stays a bare string). `action` is a dotted
lowercase verb, and the M0 set is fixed:
`account.created`, `org.created`, `org.archived`, `org.reactivated`, `org.member.added`,
`org.member.role_changed`, `org.member.removed`, `org.member.roles_changed`, `org.domain.added`,
`org.domain.removed`, `org.invitation.created`, `org.invitation.revoked`, `org.role.created`,
`org.role.updated`, `org.role.deleted`,
`agent.created`, `agent.key.registered`,
`agent.key.revoked`, `grant.created`, `grant.revoked`, `agent.token.requested`,
`agent.token.issued`, `agent.token.denied`, `tool.invoked`, `tool.denied`,
`interaction.sign_in.succeeded`, `interaction.sign_in.failed`, `connector.created`,
`connector.deleted`, `sso_connector.created`, `sso_connector.deleted`, `client.created`,
`client.updated`, `client.secret_rotated`,
`client.deleted`, `account.deleted`, `account.suspended`, `account.reactivated`,
`account.updated`, `account.security_changed`, `role.created`,
`role.deleted`, `session.logout`, `session.revoked`, `session.revoked_all`,
`consent.revoked`, `sign_in_experience.updated`, `sign_in_copy.updated`, `email_template.updated`,
`email_template.reset`, `email_connector.updated`, `email_connector.deleted`, `resource.created`,
`resource.updated`, `resource.deleted`, `webhook.created`, `webhook.updated`,
`webhook.deleted`, `webhook.secret_rotated`. Adding an action means editing
this list and the JSON Schema in `spec/events/`. The email flows of §6.1 add no actions of their
own: a self-service registration writes `account.created` (tenant chain, `{"self_service":true}`)
and `org.member.added` (org chain, role `member`), and every successful code verification writes
`interaction.sign_in.succeeded` like a password sign-in. Connector configuration is tenant-level
(`connector.created`/`connector.deleted`, payload `{"connector_id":…}`), and a first social sign-in
writes `account.created` and `org.member.added` the way a self-service registration does — with
`"social_connector"` naming the provider in both payloads. SSO connector configuration writes
`sso_connector.created` (payload `{"connector_id","email_domains"}`) and `sso_connector.deleted`
(payload `{"connector_id":…}`) on the tenant chain, and a first SSO sign-in writes `account.created`
and `org.member.added` with `"sso_connector"` in both payloads. A self-service deletion writes
`account.deleted` on the tenant chain. RP-initiated logout writes `session.logout` on the tenant
chain, with the account behind the session as the actor and the session as the subject.
Administrative revocation writes `session.revoked` (subject: the session, payload
`{"account_id":…}`, decision `deny`) for one session and `session.revoked_all` (subject: the
account, payload `{"revoked":n}`, decision `deny`) for the account-wide lever; both use the admin
as the actor.
Application management writes `client.created`, `client.updated`, `client.secret_rotated` and
`client.deleted` on the tenant chain, with the protocol `client_id` in the payload. Suspending and
reactivating an account writes `account.suspended` / `account.reactivated` on the tenant chain,
with the account as the subject; disabling also revokes its live sessions and refresh tokens.
Editing an account's display name, username or avatar from the management API writes
`account.updated` on the tenant chain, with the account as the subject, the changed `fields` and the
resulting values in the payload; repeating a value writes nothing.
Resetting an account's authenticator or removing one of its passkeys writes
`account.security_changed` on the tenant chain, with the account as the subject, `kind`
(`mfa_reset` | `passkey_removed`), the passkey id when one was removed, and decision `deny`.
Changing the hosted sign-in switches or their branding writes `sign_in_experience.updated` on the
tenant chain with the resulting values (the five methods, `mfa_enabled`, `mfa_policy`,
`mfa_trusted_devices_enabled`, `mfa_trusted_device_ttl_days`, `password_min_length`,
`password_min_character_types`, `password_reject_user_info`,
`password_reject_repetition_and_sequence`, `password_rejected_words`, `session_ttl_secs`,
`refresh_token_ttl_secs`, `sign_up_identifiers`, `sign_up_email_verification_required`,
`username_case_sensitive`, `username_min_length`, `username_max_length`,
`sign_up_profile_fields`, `captcha` (its `secret_set` boolean, never the secret),
`login_lockout_threshold`, `login_lockout_duration_secs` and the `branding` object) in the payload.
Replacing a language's hosted-page copy writes `sign_in_copy.updated` on the tenant chain with the
resulting `default_language`, the edited `language` (`null` when only the default changed) and its
`phrase_count` (`null` when `phrases` was absent). Rewording a mail purpose writes
`email_template.updated` (payload `{"purpose","subject","body"}`) and dropping the override writes
`email_template.reset` (payload `{"purpose"}`); resetting a purpose that was already default writes
nothing. Withdrawing an application approval writes `consent.revoked` on the tenant chain, with the
account as the subject and the client's `client_id`, `name` and withdrawn `scopes` in the payload.
API resource management writes `resource.created`,
`resource.updated` and `resource.deleted` on the tenant chain, with the identifier and scopes in
the payload. Organization management writes `org.created`, `org.archived` and `org.reactivated`
on the tenant chain, with the org as the subject and the slug in the payload. Membership writes
`org.member.added`, `org.member.role_changed` (payload `{"org","from","to"}`, and nothing when the
role is unchanged) and `org.member.removed` on the org chain, with the account as the subject.
Email-domain configuration writes `org.domain.added` / `org.domain.removed` on the tenant chain
with the org and the domain in the payload. Organization invitations write
`org.invitation.created` (payload `{"org","email","role","expires_at"}`) and
`org.invitation.revoked` (payload `{"org","email","invitation"}`, decision `deny`) on the tenant
chain; the sign-in that accepts one writes `org.member.added` on the org chain with the invitation
id in the payload. Organization roles write `org.role.created`,
`org.role.updated` and `org.role.deleted` on the org chain, and assigning or removing one writes
`org.member.roles_changed` with the role names before and after, with the account as the subject.
Webhook management writes `webhook.created` (payload the id, URL and events), `webhook.updated`
(payload the resulting URL, events and `enabled`), `webhook.deleted` and
`webhook.secret_rotated` (payload the id, never the key) on the tenant chain.

### §8.2 Canonicalization and hashing

Canonical bytes are **RFC 8785 (JCS)** of the event object, serialized over the event exactly as
stored minus chain fields (`prev_hash`, `hash`, `seq`). The digest:

```
hash = hex(sha256(prev_hash_bytes || jcs_bytes))
```

* `prev_hash_bytes` is the raw 32-byte previous hash (NOT its hex string).
* `jcs_bytes` is the UTF-8 JCS output (no trailing newline).
* Genesis `prev_hash` is 64 zero hex characters (32 zero bytes).
* `hash` in the API is always **lowercase hex, 64 characters**.

Rust: `serde_jcs` for canonicalization, `sha2` for the digest.

### §8.3 Append

Inside the same transaction as the business write:

```sql
SELECT seq, hash FROM <schema>.audit_chain_head WHERE singleton FOR UPDATE;  -- serializes the org
INSERT INTO <schema>.audit_events (…, prev_hash, hash) VALUES (…);
UPDATE <schema>.audit_chain_head SET seq = <new seq>, hash = <new hash>, updated_at = now()
       WHERE singleton;
```

The `FOR UPDATE` on the single head row serializes audit appends per org. M0 accepts this
contention; M3 replaces it with batched Merkle sealing (plan §12.5). Chain fields are computed
by Rust, never by a trigger — the append path must be identical from the server and from tests.

### §8.4 Verification

Computed independently of the stored chain: for each row in ascending `seq`, recompute
`hash` from the recomputed `prev_hash` and the row's JCS event; compare against the stored
`hash`. The first mismatch stops the walk.

```json
{
  "valid": false,
  "checked": 17,
  "head": { "seq": 42, "hash": "3f…" },
  "first_broken": { "seq": 18, "expected": "9a…", "actual": "b2…", "reason": "hash_mismatch" }
}
```

`reason` ∈ `hash_mismatch` | `prev_hash_mismatch` | `seq_gap` | `head_mismatch`. `valid: true`
requires `checked == head.seq - from + 1` and the recomputed head hash to equal the stored head.

| method | path | behaviour |

| GET | `/healthz` | `{"status":"ok","service":"monaca-gateway"}` |

| GET | `/bff/callback` | exchange `code` at the token endpoint, store tokens server-side, set the session cookie, 302 to `MONACA_CONSOLE_URL` |
| POST | `/bff/logout` | delete session, clear cookie, 204 |
| GET | `/bff/session` | `{"authenticated":true,"account_id":"acc_…","email":"…","tenant":"demo","orgs":[{"slug":"acme","role":"admin"}]}` |
| ANY | `/bff/api/*` | rewrite to `{MONACA_SERVER_URL}/v1/*`, attaching the session's bearer token; refresh it first when it expires within 30 s; 401 problem+json when there is no session |
| ANY | `/mcp/demo` | the demo MCP resource server (`@monaca/mcp` guard + `@monaca/module-mcp-demo`) |
| ANY | `/t/*`, `/.well-known/*`, `/v1/*` | dev proxy → `MONACA_SERVER_URL`, only when `MONACA_DEV_PROXY=1`. `/internal/*` is **never** proxied |

**BFF session cookie.** `__Host-monaca_session` in production; `monaca_session` when the origin
is plain `http://localhost` (browsers reject `__Host-` without `Secure`). Attributes: `HttpOnly`,
`SameSite=Lax`, `Path=/`, `Secure` in production only. Access and refresh tokens live in
gateway memory (M0) and are **never** sent to the browser.

**RFC 9728 Protected Resource Metadata.** For the demo resource:

* `GET /.well-known/oauth-protected-resource/mcp/demo` →
  `{"resource":"http://localhost:8080/mcp/demo","authorization_servers":["http://localhost:8080/t/demo"],"scopes_supported":["tools:read","tools:write"],"bearer_methods_supported":["header"]}`
* `GET /mcp/demo` without a token → 401 with
  `WWW-Authenticate: Bearer resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"`
  and additionally `error="invalid_token"` when a token was presented but rejected.

**401 / 403 formats (exact).**

```
401  WWW-Authenticate: Bearer resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"
403  WWW-Authenticate: Bearer error="insufficient_scope", scope="tools:write", resource_metadata="http://localhost:8080/.well-known/oauth-protected-resource/mcp/demo"
```

The 403 body is `application/problem+json` with `monaca_error_code: "MONACA_INSUFFICIENT_SCOPE"`.

**Tool → scope map (fixed for M0).**

| tool | required scope |
|---|---|
| `list_notes` | `tools:read` |
| `delete_note` | `tools:write` |

Every tool invocation is written to `/internal/audit` as `tool.invoked` (or `tool.denied` on a
scope failure) **before** the response is returned; a failure to write audit fails the request.

## §10 CI

Design rule: **pass artifacts within one workflow run** via `needs:` + `upload-artifact` /
`download-artifact`. No `workflow_run` chains — they make the feedback loop longer and the
artifact provenance murkier.

### §10.1 `rust.yml`

Trigger: `push` to `main`, `pull_request`, `workflow_dispatch`. Every job uses
`Swatinem/rust-cache` and a `paths` filter so TS-only changes skip Rust.

| job | runner | what it does | artifacts |
|---|---|---|---|
| `check` | ubuntu-latest | `cargo fmt --all` (writes, never `--check`), patch upload; then `cargo clippy --workspace --all-targets` | `rustfmt-patch` (only when the tree was not formatted) |
| `test` | ubuntu-latest | `services: postgres:18`; `cargo nextest run --workspace` | — |
| `build (windows)` | windows-latest | `cargo build --release -p monaca-server --target x86_64-pc-windows-msvc`; `napi build --release --platform --target x86_64-pc-windows-msvc` | `server-x86_64-pc-windows-msvc` → `monaca-server.exe`; `binding-x86_64-pc-windows-msvc` → `monaca-core.win32-x64-msvc.node` |
| `build (linux)` | ubuntu-latest | same for `x86_64-unknown-linux-gnu` | `server-x86_64-unknown-linux-gnu` → `monaca-server`; `binding-x86_64-unknown-linux-gnu` → `monaca-core.linux-x64-gnu.node` |
| `codegen` | ubuntu-latest | `napi build --release --dts` then `monaca-server openapi > spec/openapi.json`; regenerates `spec/events/*.json` | `codegen` → `index.d.ts`, `openapi.json`, `events/` |
| `e2e` | ubuntu-latest | `needs: [build (linux), codegen]`; stage 0 = start the server from the `server-x86_64-unknown-linux-gnu` artifact and `curl /healthz`; stage 1 = `bun scripts/e2e/skeleton.ts` | `e2e-report` → `.monaca/reports/skeleton.json` |

**rustfmt is non-fatal on branches, fatal on `main`.** Local machines have no Rust toolchain, so
contributors cannot run `cargo fmt` before pushing. `check` therefore runs `cargo fmt --all`,
uploads the diff as `rustfmt.patch`, and only fails when the ref is `refs/heads/main`:

```yaml
- run: cargo fmt --all
- run: |
    if git diff --quiet; then
      echo "formatted=0" >> "$GITHUB_OUTPUT"
    else
      echo "formatted=1" >> "$GITHUB_OUTPUT"
      git diff > rustfmt.patch
    fi
  id: fmt
- if: steps.fmt.outputs.formatted == '1'
  uses: actions/upload-artifact@v4
  with: { name: rustfmt-patch, path: rustfmt.patch, retention-days: 14 }
- if: steps.fmt.outputs.formatted == '1' && github.ref == 'refs/heads/main'
  run: |
    echo "::error::rustfmt produced changes; fix them with: bun run fetch:native --fmt"
    exit 1
```

Note the ordering: the upload is its own step, so the patch is always recorded even when the job
then fails on `main`. `--fmt` is therefore the documented local recovery path for a red `main`
`check` job. `clippy` warnings are **not** fatal during M0 bootstrap (no `-D warnings`); the
workspace declares `unwrap_used = "warn"` etc. in `[workspace.lints]`.

### §10.2 `web.yml`

Trigger: `push`/`pull_request` on TS paths. Jobs: `bun install --frozen-lockfile` →
`bun run typecheck` → `bun test` → `bun run build`. Uploads `web-build` (the vite `dist/` of both
apps) for the e2e job when it runs.

### §10.3 `image.yml`

On `main` only: build `deploy/Dockerfile.server` and `deploy/Dockerfile.gateway`, push to GHCR
(`ghcr.io/<owner>/monaca-server:<sha>` and `…/monaca-gateway:<sha>`), tags `<sha>` + `latest`.

### §10.4 `deploy-dev.yml`

On `main` after `image.yml` succeeds: SSH + `docker compose` on a VPS. When
`secrets.DEPLOY_HOST` (or any of `DEPLOY_USER`, `DEPLOY_SSH_KEY`) is absent the job exits 0
having done nothing — mode B depends on this workflow having run at least once.

### §10.5 Artifact names and destinations (contract with `fetch:native`)

| artifact name | contents | `fetch:native` destination |
|---|---|---|
| `server-x86_64-pc-windows-msvc` | `monaca-server.exe` | `.monaca/bin/monaca-server.exe` |
| `server-x86_64-unknown-linux-gnu` | `monaca-server` | `.monaca/bin/monaca-server` |
| `binding-x86_64-pc-windows-msvc` | `monaca-core.win32-x64-msvc.node` | `packages/core/` |
| `binding-x86_64-unknown-linux-gnu` | `monaca-core.linux-x64-gnu.node` | `packages/core/` |
| `codegen` | `index.d.ts`, `openapi.json`, `events/*.json` | `packages/core/index.d.ts`, `spec/openapi.json`, `spec/events/` |
| `rustfmt-patch` | `rustfmt.patch` | applied in place with `--fmt`, deleted afterwards |
| `e2e-report` | `skeleton.json`, `playwright-report/` | `.monaca/reports/` |

`fetch:native` fails loudly when an artifact is missing rather than leaving a stale binary.

### §10.6 Drift check

`codegen` compares its output with the committed files. During bootstrap — until the first
generated copy is committed — a difference is a **warning** on every ref; afterwards it **fails**
the job on `main` and warns on branches (same policy as rustfmt). Files compared:

* `packages/core/index.d.ts` — generated napi declarations vs. the committed file. The
  committed file must be napi's typedef output **as-is**; the hand-written placeholder shipped at
  bootstrap is replaced wholesale by the first codegen run, so review that first diff once
  instead of "fixing" it toward the placeholder.
* `spec/openapi.json` — generated OpenAPI vs. the committed file.
* `spec/events/*.json` — generated event schemas vs. the committed files.
* `.env.example` — every variable the code reads (a `grep`-based completeness check) must appear.

`bun test` in `web.yml` includes the differential test of native verification against `jose`
(plan §13): both must accept and reject the same tokens.
